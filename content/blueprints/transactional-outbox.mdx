<Section id="problem">

<ProblemStatement>

Every purchase must save an order in the database **and** emit an event to the message broker so payment, inventory, and fulfillment services can act.

<Pullquote>A network partition between your database commit and your broker publish is not an edge case. At 5,000 orders/sec, it is a mathematical certainty.</Pullquote>

</ProblemStatement>

</Section>

<Section id="mental-model">

<ScrollReveal>
  <InsightCard title="The Architectural Invariant">Two independent distributed systems cannot be made atomically consistent without coordination. Instead of coordinating two systems, **write the event to the same database in the same transaction**.</InsightCard>
</ScrollReveal>

The database already provides ACID atomicity. If we save the event inside the database as part of the business transaction, it is guaranteed to commit if and only if the order commits. A separate relay process then delivers the event asynchronously.

</Section>

<InPractice title="The standard CDC relay: Debezium's Outbox Event Router" sources={["Debezium: Outbox Event Router"]}>

- Debezium reads the outbox table through change data capture and expects insert-only rows. It filters out DELETE operations, so a cleanup job does not emit events.
- Its default columns are `id` (the event ID, sent as a message header), `aggregatetype`, `aggregateid`, `type`, and `payload`.
- `aggregatetype` chooses the topic (by default `outbox.event.<aggregatetype>`), and `aggregateid` becomes the Kafka message key, so every event for one order lands in the same partition, in order.
- Delivery is still at least once. Consumers deduplicate by the event ID, exactly as with a polling relay.

</InPractice>

<Diagram><IdempotentConsumerExample /></Diagram>

### The inbox: the outbox’s counterpart

The outbox makes publishing reliable; it cannot stop a redelivery. The consumer-side answer is an inbox table, which microservices.io calls the Idempotent Consumer pattern. The consumer inserts each event ID into the inbox in the same local transaction as its business update, with a unique constraint on the ID. A redelivered event fails that insert and is skipped, so at-least-once delivery still produces one effect. Prune inbox rows only after the longest redelivery or replay window has passed.

### Version the event, not just the table

An outbox payload is a public contract. Consumers you do not control may read it days later, and a replay reads it again much later still. Put a schema version in every event and make compatible changes only: add optional fields, and never rename or retype one in place. A schema registry such as Confluent’s can reject an incompatible schema before it ships. For a breaking change, publish a new event type or version alongside the old one until every consumer has moved.
