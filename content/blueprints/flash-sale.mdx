<Section id="problem">

<ProblemStatement>

An e-commerce retailer is launching a high-profile flash sale: **10,000 discounted iPhone units** made available to a waiting audience of **10 million users** at exactly 12:00:00 PM.

<Pullquote>When 10 million concurrent buyers hit one row, the database isn't slow — it's mathematically serialized.</Pullquote>

</ProblemStatement>

<ScenarioMetrics sideNote="All 10,000 units are reserved in about a second of admitted traffic. The challenge is 9.99M rejections without taking down the infrastructure." />

</Section>

<Section id="naive">

The most intuitive approach is writing directly to the relational database with an ACID transaction and row-level locking:

```sql filename="naive-transaction.sql"
BEGIN TRANSACTION;
SELECT stock FROM items WHERE id = ? FOR UPDATE;
-- if stock > 0:
UPDATE items SET stock = stock - 1 WHERE id = ?;
INSERT INTO orders (user_id, item_id) VALUES (?, ?);
COMMIT;
```

<FailureCallout title="Wait... lock contention and connection pool exhaustion occur in milliseconds!">The lock does its job: it never oversells. But it lets exactly one transaction touch the row at a time, so every other buyer waits while holding a database connection. With 2,000,000 requests per second arriving and a pool of 50–200 connections, the pool is exhausted almost immediately, and every other service sharing the database starts timing out. The failure is throughput, not correctness.</FailureCallout>

<Section id="mental-model">

<ScrollReveal>
  <InsightCard title="The Architectural Invariant">A flash sale is an **admission control problem** followed by a **reservation reconciliation problem**.</InsightCard>
</ScrollReveal>

Do not let 10 million buyers touch your transaction layer. First, shed most of the traffic at the edge and queue layers using cryptographically signed admission tokens. Second, serialize the final 10,000 item allocations in memory using an atomic Lua script in Redis. Third, confirm orders asynchronously via decoupled Kafka queues.

</Section>

```lua filename="redis-atomic-gate.lua"
-- KEYS[1]: 'stock:iphone_16'
-- KEYS[2]: 'holds:iphone_16'  (sorted set: user_id -> expiry time)
-- ARGV[1]: user_id
-- ARGV[2]: expires_at_ms (now + 10 minutes, computed by the caller)

-- 1. Idempotency: the same user clicking Buy twice keeps one hold
if redis.call('zscore', KEYS[2], ARGV[1]) then
    return 2 -- Already reserved
end

-- 2. Atomically verify and decrement available stock
local current_stock = tonumber(redis.call('get', KEYS[1]))
if current_stock and current_stock > 0 then
    redis.call('decr', KEYS[1])
    redis.call('zadd', KEYS[2], ARGV[2], ARGV[1])
    return 1 -- Success: 1 unit held until expires_at_ms
else
    return 0 -- Sold out: shed request immediately
end
```

Expired holds need a reliable way back into stock. Redis keyspace expiry events are fire-and-forget and can arrive late, so they cannot be the release mechanism. Instead, each hold is a member of a sorted set scored by its expiry time. A sweeper reads members whose score has passed and releases each one with a single `ZREM`; only if that removal succeeds does it add the unit back with `INCR`. Payment confirmation removes the same member first. Whichever action removes the hold wins, so a unit can never be both paid for and returned to stock.

```lua filename="release-expired-hold.lua"
-- KEYS[1]: 'stock:iphone_16'   KEYS[2]: 'holds:iphone_16'
-- ARGV[1]: user_id               ARGV[2]: now_ms
local expires = tonumber(redis.call('zscore', KEYS[2], ARGV[1]))
if expires and expires <= tonumber(ARGV[2]) then
    redis.call('zrem', KEYS[2], ARGV[1])
    redis.call('incr', KEYS[1])
    return 1 -- Released: the next buyer can reserve it
end
return 0 -- Already paid, already released, or not yet expired
```

Redis is the fast gate, not the source of truth. Settlement workers write each order with a conditional update, `UPDATE inventory SET stock = stock - 1 WHERE item_id = ? AND stock > 0`, and treat zero affected rows as “sold out”. That single statement cannot oversell, so it remains the final guard if a Redis failover ever resurrects a sold unit. After the sale, reconcile Redis holds, orders, and payments, and refund any mismatch.

Fairness belongs in the waiting room. Commercial waiting rooms such as Queue-it give everyone who arrived before the start time a random place in line, so refreshing early or running bots gives no advantage. Buyers who arrive after the start join the back of the queue in order.

<InPractice title="Real sales shed load before it reaches stock">

- Queue-it's waiting room can give early arrivals a random place in line, then sends visitors on to the store at a rate the store chooses. The store's servers only see the outflow, never the full rush.
- Amazon's Builders' Library advises rejecting excess requests early and cheaply, so a server spends its capacity finishing the work it accepted instead of starting work that will time out.
- Redis runs a Lua script atomically: no other command runs while it executes, so the stock check and the decrement cannot interleave. Replication is asynchronous, and even `WAIT` does not stop a failover from losing acknowledged writes, which is why the database keeps the final guard.

</InPractice>
